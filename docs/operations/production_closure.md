## Incidents, alerts and rollback

The platform operator owns acquisition/publication failure, stale input, readiness failure, accounting imbalance and audit/manifest mismatch alerts. The ML owner owns feature incompatibility, failed jobs and drift/outcome metrics. The security owner owns authentication anomalies and audit tampering. Before production, configure and test an Azure Monitor action group with the named on-call destination and escalation recipient. Route sustained readiness failure, any terminal pipeline failure, any failed integrity/accounting gate and failed feedback transfer to it. Agree debounce windows, workload/traffic baselines and escalation deadlines with the owner; none is currently approved. Preserve an injected failure's correlated log, fired alert and received notification. Application Insights resources and process counters alone do not pass this acceptance.

On corruption: stop publishing/writing, retain run/correlation IDs and failed receipts, restrict operator access, preserve originals, and verify a new restored directory using the documented backup/restore CLI. Never clear audit rows or repoint to an unverified product to make readiness green. On source outage: retain the last approved release, expose freshness/unavailability, and retry with a new run ID after source recovery. On feedback timeout: mark transfer pending/unknown, inspect destination audit IDs, and retry the same packet; never infer completion from upload.

Rollback uses the previous digest-pinned image and compatible schema/contract, prior accepted Fabric snapshot and prior explicitly promoted model. Restore locally to a new directory first, compare publication and audit manifests, then switch the data-directory configuration. A newer SQLite user_version is rejected; do not decrement it to force old code to open it. Retain both snapshots until owner approval. Cloud backup, real failover and business RPO/RTO remain unverified until executed under the approved workload.
